# SPEC-005 Validation Guide (for implementation phase)

This file lists validation scenarios for a later implementation phase. It does not claim the feature is implemented and none of these commands were run during `$speckit-plan`.

## Prerequisites

- Run from the repository root on `005-field-management-region-resolution`.
- Use the repository-pinned Node/pnpm toolchain and generated API client workflow.
- For writable PostgreSQL/PostGIS integration tests, verify the target database name is exactly `ekim_hasat_test` before connecting. Never point feature fixtures at another database.
- Use two Businesses and memberships with separate Fields for authorization checks.
- Use deterministic test resolver adapters: separate administrative and agricultural outputs, partial resolution, no coverage, unavailable dataset, and stale-result cases. These are test adapters only, not production data.

## Validation scenarios

1. **Authorized list and detail**: As a member, list Fields ordered by `(name ASC, id ASC)` at default 50 and maximum 100; follow opaque cursors and check no duplicates/omissions for unchanged names. Test empty state, duplicate names, malformed cursor, and a rename between pages. A member of a second Business cannot enumerate or inspect the first Business's Field.
2. **Create point and Polygon Fields**: Create using a map point and the existing location-permission fallback; separately create a valid Polygon. Confirm point-only has no current boundary, Polygon representative point is server-derived by the existing method, and a new Polygon is unverified. Reject malformed/out-of-range geometry without reporting success.
3. **Default labels, idempotent create, and name edits**: Seed gaps among generated labels, then issue simultaneous blank-name creates in one Business and verify each receives a distinct first-available `Tarla N`. Repeat across separate Businesses. Retry one successful create with the same `Idempotency-Key` and identical normalized payload in the same user/Business/`CREATE_FIELD` scope after simulating a lost response; confirm the durable canonical result is returned and no second Field or label is allocated. Reuse that key with changed payload or authenticated/Business/command context and confirm `IDEMPOTENCY_KEY_REUSED`; confirm another context never replays the result. Verify concurrent same-key requests persist one canonical outcome in the generalized `BusinessCommandIdempotencyRecord`; do not use the onboarding `IdempotencyRecord`. Confirm trimmed duplicate farmer-entered names are allowed. For update, confirm omitted `name` preserves the existing name, blank/whitespace-only input is rejected, and no update allocates or resets to `Tarla N`.
4. **Current state transitions and versions**: Update Polygon to Polygon, Polygon to Point, then Point to Polygon. Confirm pointer behavior, monotonically increasing boundary version, and retention of every prior geometry. Confirm stale `If-Match` gets the existing HTTP 409 `STALE_VERSION` response and does not overwrite newer state. In mobile, verify attempted edit values remain in the active edit session, the latest canonical Field is loaded and shown with a clear conflict, and no further mutation occurs until explicit farmer action; do not auto-merge/rebase or silently retry.
5. **Region coverage and failures**: Test administrative-only result, agricultural-only result, both results, no coverage, invalid geometry, stale data version, and unavailable resolver data. Valid Field create/edit always succeeds; unsupported results remain visibly unresolved. Check source, confidence/quality, data version, and server `resolvedAt` on every resolved value; confirm `resolvedAt` is the acceptance time and is distinct from dataset publication date. Do not rely on provider-specific payloads.
6. **Override precedence**: Set an explicit agricultural override, change point and Polygon, deliver later resolver results, and verify the override stays effective. Clear it explicitly and confirm the current automatic suggestion becomes effective only when resolved; otherwise remain unresolved.
7. **Season history**: Activate a Season against a current Polygon and resolved/overridden region context. Confirm the new snapshot stores exactly `Field.currentBoundaryVersionId` and the current administrative/agricultural states and values, source, confidence/quality, `dataVersion`, `resolvedAt`, and manual override state/value. Repeat with a point-only current Field that retains old Polygon history and confirm the activation snapshots null without falling back to historical versions. Then change Field name, point, boundary state, and region; confirm the activation snapshot remains unchanged. Verify Field detail exposes only a small read-only ACTIVE summary.
8. **SPEC-004 weather behavior**: Store/read weather tied to the current representative point, change the representative point, and confirm prior-point weather is unavailable. Verify a later valid refresh for the new point is accepted using the existing lock/recheck/fingerprint rules. Separately change Polygon while retaining the same representative point and confirm region resolution key changes without changing weather semantics.
9. **Mobile failure states**: On mobile, deny location permission and complete point/Polygon selection; assess loading, empty, denied, retryable network failure, invalid geometry, stale-`If-Match` conflict recovery, and success only after server acceptance. Confirm accessible labels/statuses and that no offline Field mutation is queued or shown as successful. Create retries use the same `Idempotency-Key`; Field update conflicts remain governed by `If-Match`.
10. **Asynchronous accessibility**: Keep each flow screen open while loading completes, save succeeds/fails/conflicts, and region resolution becomes resolved/unresolved/unavailable. Confirm visible result text remains present and a screen/form-level accessible announcement occurs for each meaningful transition not communicated by focus, including save success, failure/conflict, and region result/unavailable. Re-render or repeat the same state and confirm no duplicate announcement; do not rely on color alone. Verify implementation against repository accessibility conventions. Physical VoiceOver/TalkBack validation is not claimed by this planning guide.
11. **Existing Fields and migration preservation**: Seed Fields with multiple historical boundary versions, duplicate `(fieldId, version)` ties with different IDs, a single boundary, and no boundaries, plus snapshots referencing historical versions. Verify the pre-SPEC-005 activation selector (`version DESC, id ASC`) identifies the current boundary. Apply the migration with resolver adapters unavailable against exactly `ekim_hasat_test`; confirm the new pointer selects that exact row including the tie winner, Fields without history remain null, every history row ID/version/geometry and snapshot reference is unchanged, and no uniqueness constraint forces legacy rewrites or a Polygon creation. For a legacy null current-region pointer, confirm list/detail/normal edits continue and Field detail displays both region suggestions as `UNRESOLVED`; the generic list need not include region status. Confirm no resolver call, inferred region value, or region row is written. Invoke the bounded resolution operation twice for the same current location key and source-data versions and confirm idempotent state; change location before accepting a prior result and confirm stale-result discard. Confirm manual override preservation and unresolved state when no source qualifies. No scheduler or whole-database region backfill is required.
12. **Future activation only**: Preserve a pre-existing `SeasonContextSnapshot`, then activate a different draft Season after SPEC-005 is active. Verify the activation reads the current boundary pointer exactly (including null), snapshots the current region context with all accepted provenance and override fields, and projects a null region pointer as two explicit `UNRESOLVED` states with no override. Verify it does not issue a version-ordered boundary lookup. Compare the pre-existing snapshot before/after and confirm it is unchanged. Run all writable cases exclusively against verified `ekim_hasat_test`.
13. **Production navigation**: Run the mobile route-level integration test and confirm the approved navigation positions are `Bugün | Takvim | Tarlalar | + | Daha Fazla`; Tarlalar opens the authorized list, a Field opens detail, and add-field opens creation. Confirm the implementation preserves unrelated route meanings and adds no Calendar flow.

## Existing commands to identify during implementation

Use the relevant scripts already defined by the repository's package manifests and test files for API unit/integration tests, mobile feature tests, OpenAPI generation/contract checks, and type checking. Add/adjust tests first for changed behavior. Verify generated client output is reproducible from `contracts/fields.openapi.yaml` and its registered generator mapping. The integration command must explicitly set a connection string whose database path is `ekim_hasat_test` and verify `current_database()` before mutating fixtures.

## Expected outcome

All scenarios pass with database-backed geometry, transaction/concurrency, tenant-isolation, snapshot immutability and weather tests using the real PostGIS semantics where applicable. No resolver absence or outage blocks Field management; a result is presented as resolved only with valid current provenance.
