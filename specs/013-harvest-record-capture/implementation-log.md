## Implemented behavior and architecture

- Harvest is a canonical, immutable historical fact in the Harvest domain and API module. `POST /v1/fields/{fieldId}/harvests` accepts a stable client-generated `harvestId`; PostgreSQL stores the business-scoped identity, Field/Season associations, actor and membership provenance, and UTC acceptance time. Prisma migrations own the schema and the database trigger rejects UPDATE and DELETE.
- OWNER and WORKER may create; ADVISOR cannot create but retains ordinary authorized Field/Season Diary read access. The server resolves current membership and business, checks role and Field/Season scope before creation or replay disclosure, and never treats a client role or business ID as authority. Diary response-level `viewerRole` is server-derived from `MembershipScopeService`; mobile uses it solely for the eligible active-Season create CTA and fails closed when it is absent.
- First acceptance requires an ACTIVE Season belonging to the authorized Business and Field. Exact replay is not a new acceptance: current actor authorization and same-context access are revalidated, then actor, Field, Season and payload are compared with the accepted fact. A later Season lifecycle change does not invalidate an authorized exact replay. Changed identity content or authorized context conflicts; missing or foreign context remains privacy-safe.
- One `(businessId, harvestId)` identifies one fact. The write transaction locks the Business row before lookup, serializing same-Business submissions; the composite unique key protects identity. Exact concurrent/retried submissions converge on the original accepted result; changed actor/context/payload yields an idempotency conflict. Different Businesses have independent identities.
- `harvestDate` is a validated local calendar date stored as PostgreSQL `DATE`, without an occurrence time. First acceptance rejects dates after authorized Business-local today or before actual planting; equality at planting is valid. Quantity is a positive exact decimal string, at most 11 integer and 3 fractional digits, stored as unconstrained exact `NUMERIC` with range and scale checks; no binary-float canonicalization, rounding or unit conversion. Each record retains its chosen `KG` or `METRIC_TONNE` unit.
- The existing SPEC-006 Field/Season Diary projects canonical Harvests as distinct `HARVEST` entries. `includeHarvests` defaults false for existing clients and mobile opts in on every page. Default V1 behavior remains; opt-in uses V2 with Field/Season, flags and Business timezone binding. Legacy Expense V2 cursors without the Harvest flag mean false. Timed entries precede date-only entries within a local day; date-only kind and descending UUID provide deterministic continuation. Traversal is keyset-based, not a fixed snapshot.
- Capture is online-only from the active Season Diary, with Field and Season fixed. No Harvest outbox or offline persistence is added. An uncertain response keeps the same ID and unchanged payload only in the active form for a user-initiated retry; the UI reports success only after server confirmation and returns to the Diary with feedback. The Impeccable hardening pass added success feedback, Android system Back handling, selected/expanded unit accessibility state, and Turkish invalid-date correction.
- No note, correction/edit/delete/void, sales, revenue, disposition, inventory, grading, unit conversion, or generalized finance/analytics feature was added. See [spec.md](./spec.md), [data-model.md](./data-model.md) and [contracts](./contracts/) for the authoritative boundary.
