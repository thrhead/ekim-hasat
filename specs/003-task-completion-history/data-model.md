# Data Model: Task Completion and History

This is the SPEC-003 planning model. PostgreSQL remains canonical; Prisma owns the API migration. Mobile SQLite stores only the actionable Today snapshot and completion-specific commands/results required by this feature. No generic sync schema is introduced.

## Task Completion (server operational record)

One accepted record states that a planned task was carried out. It is separate from and does not mutate `PlannedTask`.

- `id`: UUID generated by the mobile client when the farmer presses Complete. This is the stable `completionId` and idempotency identity.
- `plannedTaskId`: required reference to the original planned task; unique so a task cannot acquire multiple accepted completions, including under concurrent requests.
- `seasonId`, `fieldId`, `businessId`: server-derived scope/context references. They are not accepted from the command as authorization claims.
- `actorUserId`, `actorMembershipId`: authenticated user and active membership that submitted the accepted command; persisted for historical integrity and authorization/audit. Actor attribution is not part of the normal farmer-facing history response or UI in SPEC-003.
- `occurredAt`: absolute instant supplied by the client for the original Complete action, stored as timezone-aware UTC instant. A replay or delayed synchronization never replaces it.
- `recordedAt`: server-assigned instant when the completion is committed.
- `baseTaskVersion`: planned-task version observed in the locally available Today snapshot and submitted with the command.
- `payloadFingerprint`: canonical fingerprint of task identity, `occurredAt`, and base version. Reuse of a completion ID with changed command data conflicts.
- `taskTitleSnapshot`, `plannedLocalDateSnapshot`: planned intent as it stood when the server accepted completion. These fields preserve a stable history row if later product capabilities permit task edits.
- Plan provenance: retained through references to the immutable active `SeasonPlan`, its source snapshot, and `SeasonContextSnapshot`; do not copy or rewrite template content in a completion.
- No server synchronization state is stored on this row. Existence means server accepted; `pending` and `conflicted` are mobile command states only.

### Integrity and lifecycle

- The row is append-only for this feature; no completion edit, delete, undo, void, or correction command is added.
- Unique `id` provides durable request replay; unique `plannedTaskId` settles distinct-ID races for the same one-time planned task.
- Business/season/field/task relationships must be consistent. Use migration-backed foreign keys and unique constraints, adding composite keys where needed so tenant scope is structurally checkable as well as query-enforced.
- Index accepted history by `(fieldId, occurredAt DESC, id DESC)` and `(seasonId, occurredAt DESC, id DESC)` for the bounded field/season page query; retain the unique task and completion identity constraints.
- The migration must be additive and backward-compatible. It must not rewrite existing seasons, tasks, or activation snapshots.
- The completion insert and any required audit evidence commit atomically. No server background job or event outbox is needed unless an in-scope asynchronous consumer is later identified; notifications are not in this feature.

## Today task snapshot (mobile SQLite)

A focused cached projection of the most recent server-authorized `/today` response enables offline completion only for tasks already locally available.

- Local account partition, task ID, season ID, field ID, title, crop display label, source kind, planned local date, and `taskVersion` from the API.
- Business-local date, resolved Business IANA timezone, and fetch time from the same server response.
- Replaced atomically on successful `/today` refresh; unresolved completion commands retain their own task snapshot and are never deleted by this refresh.
- Device timezone never supplies the cached Business date or timezone.
- Stale cached rows are not presented as a fresh server reading. Offline UI identifies the last server-provided Business-local date and keeps locally pending/conflicted completion state explicit.

## Completion command (mobile SQLite, completion-specific outbox)

One row per locally recorded completion action, behind an injectable task-completion storage interface.

- `accountId`, `completionId`, `taskId`, captured `occurredAt`, `baseTaskVersion`, and the minimal task/field/season display snapshot.
- `state`: `PENDING`, `ACCEPTED`, or `CONFLICTED`.
- `serverResult`: accepted public completion result, retained transactionally with transition to `ACCEPTED`. `recordedAt` remains server-side audit/commit metadata and is not required in the public response or local persistence model.
- `conflictCode` and safe server task/completion summary when available, retained with transition to `CONFLICTED`.
- Retry metadata sufficient for safe diagnostics/retry; never store credentials or tokens in the command.
- Unique `(accountId, completionId)` and at most one local `PENDING`/`ACCEPTED` command per `(accountId, taskId)`; allow multiple pending completions for different tasks and retain older conflicted attempts. Do not send `businessId` as authorization input.

### Local state transitions

```text
PENDING ── committed server result durably saved ──> ACCEPTED
PENDING ── stale task/season or competing completion ──> CONFLICTED
PENDING ── current Membership revoked ──> CONFLICTED
CONFLICTED ── explicit review and new command identity ──> new PENDING row
```

- `ACCEPTED` is terminal and may appear in local history.
- `CONFLICTED` is not presented as accepted completion. Preserve original intent and any server state; do not auto-rebase or delete it. Where current Membership still authorizes a refresh and the task remains actionable, recovery requires farmer review and explicit reconfirmation with a new completion ID and current base version. Preserve the original `occurredAt` because the real work did not happen again during conflict review.
- A repeated exact request with the same completion ID never creates another completion. A different completion ID for a task already completed returns a stable `TASK_ALREADY_COMPLETED` conflict with the authorized canonical completion summary.
- Membership denial is privacy-safe and is checked before replay/history access. A locally queued command remains durable and visibly conflicted; it does not obtain server authority from the earlier online read.

## API view models

- **Today task**: existing task summary plus additive `taskVersion`; the response also includes resolved `businessTimezone`, alongside the existing `localDate`.
- **Accepted completion**: farmer-facing history representation contains completion ID, task/season/field identity, immutable task title and planned local date snapshots, `occurredAt`, and plan source/provenance summary sufficient for the field/season history view. `occurredAt` is rendered in Business timezone. `recordedAt` remains persisted audit/synchronization metadata and is not required in the normal farmer-facing row. Actor user/membership fields remain stored for audit but are not returned for farmer-facing attribution.
- **Task-completion history page**: accepted completion items only, Business timezone, and a next cursor. Optional season filter is validated against the authorized field. Order by `occurredAt DESC, completionId DESC`; default page size 50, maximum 100.
- Pending and conflicted items are local device state and are not returned by server history as accepted facts.

## Relationships

```text
Business 1 ── * Field
Field 1 ── * Season
Season 1 ── 1 SeasonPlan
SeasonPlan 1 ── * PlannedTask
PlannedTask 1 ── 0..1 TaskCompletion
Season 1 ── 1 immutable activation context (for ACTIVE seasons)
ApplicationUser 1 ── * TaskCompletion (actor)
Membership 1 ── * TaskCompletion (authorized actor context)
Account 1 ── * local TodayTaskSnapshot
Account 1 ── * local TaskCompletionCommand
```
