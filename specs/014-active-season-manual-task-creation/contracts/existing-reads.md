# Existing Read and Action Contract Changes

This is a planning amendment, not a second implementation of an existing endpoint. Maintain the canonical contracts under SPEC-002, 003, 006, 007, 008 and 009 and update them additively only where required; regenerate their shared client types. Old installed mobile versions must continue to parse responses.

- **Season setup/approved plan (SPEC-002):** `plan.tasks` represents original plan membership, not a list of tasks added after activation. Preserve draft behavior, existing original task fields/current adjustment behavior and source. Do not replace the immutable approved snapshot with live additions or silently rewrite it.
- **Today and Calendar (SPEC-002/007):** include accepted operational tasks under existing authorization, status/date/grouping and pagination rules. Expose task-level `sourceKind` where needed as an additive compatible field. Keep plan context/source distinct from task origin. For a post-activation manual task, task source is MANUAL and task template version is null; the plan may truthfully remain VALIDATED_TEMPLATE. Saved Calendar snapshots continue existing freshness and scope rules. Pending local items are visibly separate and never part of a canonical response.
- **Task detail and actions:** use existing identifiers and task version, with unchanged completion, offline completion, date adjustment, skip, concurrency and current authorization semantics. Do not expose task actions as accepted while task creation is pending. New create role does not alter other actions' roles.
- **Completion and skip/history (SPEC-003/009):** accepted manual tasks' result, replay, and history task provenance must resolve MANUAL and null template version, including paths previously reading plan/snapshot source. Legacy tasks retain their old source behavior. Existing completion and skip facts, audit/time snapshots and sorting remain unchanged.
- **Diary (SPEC-006):** existing completion/skip projections continue their existing inclusion, filters, order and cursor behavior. Creating a task alone adds no invented diary event. Test whether provenance is exposed in each existing projection; if so resolve it from task origin.
- **Owner-only affordance:** use a previously authorized OWNER signal in existing context or an additive server-derived role indicator to show capture fail-closed, including offline continuity. It is presentation context only; server checks are authoritative. Do not infer OWNER from user-editable metadata or create a generic capability framework.

- **Create error handling:** Use the feature contract error code to distinguish invalid input, ineligible season, identity conflict and access denial. A response to a later attempt cannot resolve a possibly committed earlier attempt by itself; preserve unconfirmed status until authoritative evidence establishes the outcome. Retry only transient failures automatically; definitive rejections require explicit farmer action.
