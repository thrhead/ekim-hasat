# Implementation Plan: Calendar / Takvim

**Branch**: `007-calendar` | **Date**: 2026-10-06 | **Spec**: [spec.md](spec.md)

## Summary

Implement the existing mobile Takvim destination as a read-only Calendar backed by an authorized API boundary that creates short-lived, coherent Calendar read projections for pagination. The server returns canonical unfinished planned work for ACTIVE seasons, derived overdue status, Business-local date context, month work indicators, and read-only detail context. The mobile client provides an agenda for one selected date, a secondary month overview, an optional authorized Field filter, and a Calendar-specific read-only SQLite saved view that is usable only after a retryable connectivity failure and only for provably complete requested coverage.

## Technical Context

**Language/Version**: TypeScript; existing workspace package versions.
**Primary Dependencies**: Existing NestJS/Fastify API, Prisma, Expo/React Native, generated API transport conventions, and SQLite mobile persistence.
**Storage**: PostgreSQL via Prisma remains canonical and stores short-lived Calendar-only server read projections for coherent pagination. The mobile client separately stores complete read-only Calendar views in the existing SQLite database. No new datastore or generic cache/sync layer.
**Testing**: API unit/contract/integration and tenant-isolation tests; mobile store/unit and screen tests; offline eligibility, account/Business isolation, accessibility semantics, and request-race tests. Actual device validation must be reported only if performed.
**Target Platform**: Existing iOS and Android mobile apps; API server.
**Project Type**: Mobile + API modular monolith.
**Performance Goals**: Month overview limited to one Business-local month; task groups returned in fixed pages of at most 50 rows; avoid loading all month/season task rows. No unsupported latency target is introduced.
**Constraints**: Server-authoritative membership/Field access; dates use Business timezone and canonical local-date values; completion is excluded by canonical completion relation; saved reads never authorize; only retryable connectivity failures permit saved data; no task mutations or generic sync.
**Scale/Scope**: Month-indicator coverage for one Business-local month, task rows for one selected date, all qualifying overdue attention items, and one optional Field scope. Queries and cursors must remain bounded; no season-wide agenda or full-month task-row prefetch.

## Architecture and Data Flow

1. On initial Calendar open, the mobile client omits `selectedDate`; it never derives the initial date from device timezone. The Calendar API resolves and returns the authoritative Business-local date, which becomes the selected date in the UI. When the farmer selects another date, the client supplies that explicit date and uses the resolved date returned in the new read.
2. A new Calendar read module resolves the authenticated identity to the active Business membership using existing scope services. It resolves Business timezone on the server and validates optional `fieldId` against authorized Business scope.
3. A dedicated Prisma repository reads only incomplete planned tasks whose Season is ACTIVE and plan is APPROVED, scoped through authorized Business/Field ownership. It returns the selected date, the one Business-local month containing that date, and disjoint task groups: overdue tasks have `plannedLocalDate < businessLocalToday`; selected-date tasks have `plannedLocalDate = selectedDate` and are not overdue. Thus when a past date is selected, its tasks remain only in the overdue group. Month indicators include qualifying tasks on their original planned dates, including overdue work. Overdue is derived and never written back.
4. The API creates one Calendar-specific immutable read snapshot in a single PostgreSQL `REPEATABLE READ` transaction. Its first statement establishes the MVCC snapshot and captures the database statement-start UTC `asOf`. Authorization resolution is delegated to the existing `MembershipScopeService` boundary with this exact `Prisma.TransactionClient`; the service uses the supplied client without opening a nested transaction. Existing callers omit the client and retain their current public API and transaction behavior. The same transaction then resolves the authoritative Business timezone (using the existing `Europe/Istanbul` fallback), derives Business-local today from that `asOf`, validates an explicitly supplied `selectedDate` or uses Business-local today when omitted, validates the optional Field, and selects month indicators plus task projections. The integration RED test must prove authorization and projection reads share the same repeatable-read view. The resolved `selectedDate` is returned and bound into the read identity. It stores at most 31 month indicators on the snapshot row and task projections as immutable rows under one server-generated opaque `readId`; publication is atomic. This is a point-in-time view of canonical state at `asOf`; canonical tasks are not locked or mutated after capture.
5. The mobile client requests the displayed month indicators and renders only the selected date plus overdue group in the agenda. Date selection changes the agenda date; it does not mutate or redate tasks. Field selection is applied to all API projections. Offline selection is available only for exact dates/scopes with a fully loaded saved task set; month indicators do not prove task-list coverage for another date.
6. Tapping a row opens read-only details from the Calendar read model while retaining task and selected-date context. Calendar has no path to Today completion commands or mutation APIs; Today remains execution, History/Diary remains completed history.
7. On retryable connectivity failure only, the client may render a saved snapshot when account ID and Business scope match, the exact selected date and requested Field scope are covered, and all required selected-date and overdue task pages plus month indicators are complete. A snapshot need not contain task rows for every date in the month; a date is covered only if that date's complete task set was loaded and saved. Coverage uncertainty, missing pages, an uncovered date/Field, and explicit auth denial produce unavailable state. Saved state is visibly stale/read-only.

## API Contract Direction

Use a Calendar-specific authenticated read-snapshot creation operation under the existing `/v1` API (`POST /v1/calendar/reads`) with optional Business-local `selectedDate` and optional `fieldId`; do not accept `businessId` as authorization input. If `selectedDate` is omitted, resolve the authenticated user's current Membership and authorized Business, resolve the server-authoritative Business timezone with the existing fallback, and derive the current Business-local date from the server clock within the read transaction. If supplied, validate and use that date. Return the resolved `selectedDate` explicitly. It persists only a short-lived immutable projection, not farming-domain state. The month is derived from the resolved selectedDate. The result includes a server-generated opaque `readId`, `asOf` transaction-start time, Business timezone/today, scope facts, month indicators, active-season/work facts, and first pages for overdue and non-overdue selected-date groups. Continue pages through an authenticated read operation using that `readId` plus an opaque cursor.

The server-generated `readId` is a lookup key, not a bearer credential. Its persisted record binds the verified user and membership, server-resolved Business, authorized Field scope (all authorized Fields or one validated Field), resolved selected date, Business-local today/timezone, derived month boundaries, eligibility predicate/version, ordering, `asOf`, and expiry. An omitted initial date resolves to Business-local today; an explicit date is validated and used. Every explicit date or Field selection creates a new read identity. Continuation requests resolve and lock/revalidate the current active membership/default-Business context and revalidate Field access in their own database transaction before returning stored projections. Each cursor is a random server-issued token recorded against the `readId`, result group, and stable last key; a uniqueness rule for `(readId, group, last key)` makes replays return the same continuation token. Unissued or cross-group tokens are rejected. The server obtains later pages only from immutable snapshot rows, never by rerunning the live task query.

Use stable ascending order `(plannedLocalDate, taskId)` for each group. Snapshot rows and indicators are immutable after creation, so concurrent canonical task creation, completion, Season/plan-state changes, or other eligibility changes cannot shift page boundaries: every page describes the canonical state visible to the read transaction. Changes committed after that transaction appear in a newly created read, not merged into this one. Replaying an issued cursor returns the same page; expired, unknown, malformed, cross-user, or invalidated read identities return a non-data error and never a partial continuation. Membership/authorization failure is returned before snapshot data and cannot activate client cache fallback.

The snapshot has a Calendar-specific short lifetime (15 minutes). Its parent `readId` is the primary key; task projection and cursor rows have required parent foreign keys with `ON DELETE CASCADE`, while projection `taskId` deliberately has no foreign key to canonical tasks so later canonical deletion/change cannot rewrite or erase a captured read. Cursor tokens are unique, cursor retries are also unique by `(readId, group, lastKey)`, and an index on snapshot `expiresAt` supports bounded request-time pruning of a fixed small batch of expired parent reads. Expiry is enforced on access regardless of pruning. No scheduler, worker, generic snapshot service, event store, lease, or synchronization platform is introduced. Task detail context is part of each task projection so online and saved read-only details preserve the same task/date context. API types follow generated OpenAPI client conventions.

## Saved Calendar Read Model

Use separate SQLite tables in the existing mobile database, not the Today snapshot or mutation outbox. Partition each saved view by authenticated account and server-resolved Business scope. Persist the resolved selected date returned by the server, the covered Business-local month and its indicators separately from task-row coverage, covered Field scope (all authorized Fields at snapshot creation or exactly one validated Field), task rows and original dates, overdue classification inputs, Business timezone/current-date metadata, retrieval time, server `readId`, and page-chain/completion state. Do not persist credentials or treat this record as proof of current membership. Month metadata may be reused for the covered month; task rows cover only the exact resolved selected date and complete overdue set captured by that read.

Only complete saved views qualify. The client stages pages under one `readId`; each response must echo the same read identity and query scope, including Business, Field set, selected date, month, and `asOf`. Fetch one cursor at a time per group, following only the `nextCursor` from the preceding accepted page; retry the same cursor when needed. Validate the echoed consumed cursor, and upsert rows idempotently by read/group/task ID. A gap, unexpected cursor response, or mismatched identity invalidates that staged read. Promote a local saved view atomically only after the initial response supplied complete month indicators and both full cursor chains for `selectedDateTasks` and `overdueTasks` reached terminal pages for the same `readId`, before the server read expires. Expiry invalidates incomplete staging, but does not revoke a locally complete saved view already promoted before expiry. Month indicators cover the month but do not prove task-row coverage for another date. An offline date change is allowed only where a complete saved view exists for that exact date plus the complete overdue set and month indicators for the requested Field scope. A Field-filter change is allowed only when saved rows and coverage metadata fully include that Field (an all-Fields snapshot retains all included Field partitions). Never combine read identities or speculatively merge partial results.

If a page request fails retryably, an already-complete local saved view may be used only when it independently covers the requested date/Field; in-progress rows are never exposed as fallback. If the server snapshot expires or a cursor/read identity is invalid, discard that staged read and restart from a newly created `readId` when online. If restarting is impossible, show unavailable unless a separately complete matching local saved view exists. Never append pages from a new identity to old staging rows. Authentication/authorization errors, revoked/unknown session or membership, and known access loss must clear/withhold display and never activate fallback. A new authenticated authorization context must not inherit another context's data. A server success replaces the matching local saved view atomically only after complete coverage is assembled. No background sync, mutation outbox, leases, or generic reconciliation is added.

## Accessibility and Interaction Architecture

Use native/adaptive controls consistent with the existing mobile UI and Impeccable's advisory guidance. Agenda is the default. Date selection, Field filter, task rows, month work indicators, loading/error/empty/saved messages expose meaningful accessible names, state, and focus behavior. Month indicators communicate presence of work without task names; visual encodings remain a later design choice as long as assistive technology can identify dates with work. Saved/offline messaging must distinguish saved and potentially outdated information from current server data. Keep touch targets, system text scaling, platform navigation/back behavior, and reduced-motion behavior consistent with existing iOS/Android patterns. No visual styling or additional product behavior is fixed by this plan.

## Request Races and State

Date or Field changes can issue overlapping requests. The screen must use a monotonically increasing request generation (or equivalent cancellation plus identity check) keyed by account, Business authorization context, selected date/month, and Field filter. Only the latest matching request may update visible state or the saved snapshot. On account/Business context change or sign-out, clear in-memory Calendar view state and ensure persisted data remains inaccessible outside its exact partition. A stale response must not replace a newer view or snapshot.
